本仓库没有统一的错误类型体系或中间件，而是按“抓取脚本”和“纯前端静态站点”两条线各自采用最简策略。

1. Python 抓取脚本（scripts/scrape.py、scripts/update_monthly.py）
- 外部依赖缺失：在 import requests 失败时自动通过 subprocess 调用 pip install 安装后再重试，属于“自修复式”容错。
- 网络请求：所有 requests.get 调用均包裹 try/except Exception，403 会打印 rate limit 信息并 sleep 后返回空结果；其他异常一律捕获并 print 到 stdout，函数返回 None 或 []，让上层流程继续执行。
- 数据解析：对 JSON 字段使用 dict.get 并提供默认值，日期解析用 try/except (KeyError, TypeError, ValueError) 兜底为 0，避免单条脏数据导致整个流水线崩溃。
- 文件 I/O：写入 data/repos.json 前 os.makedirs("data", exist_ok=True)；月度合并脚本读取旧库时用 FileNotFoundError 分支初始化空结构。
- 整体风格：不抛出自定义异常，也不记录结构化日志，错误以 print 输出并通过返回值降级，保证单次运行尽可能产出部分结果。

2. 前端展示（web/app.js）
- 数据加载：loadRepos 尝试多个 URL（DATA_URL、./data/repos.json、data/repos.json），任一成功即继续；全部失败则 throw new Error('Data file not found')，外层 catch 渲染带中英文提示的骨架占位，区分 file:// 协议与需要运行抓取器两种场景。
- 本地存储：loadBookmarks/saveBookmarks 用 try/catch 包裹 localStorage 读写，JSON.parse 失败回退为空集合，确保离线浏览不受损坏缓存影响。
- 交互逻辑：收藏、筛选等局部操作也各自 try/catch，单个 UI 状态异常不影响全局页面。

3. 约定与建议
- 新增抓取源时应沿用“try/except Exception + 返回空值/默认值 + 控制台打印”的模式，不要中断主流程。
- 对外暴露的错误仅在前端 loadRepos 顶层统一捕获并转为用户可读文案，内部保持静默降级。
- 如需增强可观测性，可在现有 print 处追加结构化日志（如 JSON 行），但当前仓库未引入任何日志框架。
